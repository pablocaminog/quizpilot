# QuizPilot execution plan

## Context
Create QuizPilot as the first of four independent portfolio applications: a Kahoot-style live quiz product where a host describes a learning goal in chat, selects a source (URL, text document, pasted text, or original AI generation), reviews the generated quiz, publishes it, and runs a real-time game. Build the customer experience in Astro JavaScript with shadcn/ui, and use Cloudflare Kitesurf to obtain rendered public webpage content for URL-based quizzes. The app must be deployed into the host's own Cloudflare account through a Deploy to Cloudflare flow; Cloudflare authorization is required, so the UI must not claim anonymous deployment.

The implementation will use Flue (`@flue/runtime`) for the persistent host drafting conversation and a separate application-owned Durable Object for live-room state. This split preserves Flue's agent durability while keeping WebSocket admission, scoring, and fan-out under deterministic server control.

## Findings
- `orders-demo` is a separate Hono/Workers/D1 order-management demo with an existing engineering-agent controller; it is a reference for Cloudflare Worker configuration and test conventions, not a target for QuizPilot code.
- Cloudflare Wrangler deployment requires OAuth or another authenticated account credential. The deploy call-to-action therefore means one-click setup after authorization, not deployment without an account.

- Flue's Cloudflare adapter uses `@flue/vite` before `@cloudflare/vite-plugin`; scanned `'use agent'` exports become durable agent classes. Each added agent requires an appended `new_sqlite_classes` migration in `wrangler.jsonc`; an HTTP route is required only when the application exposes the agent over HTTP.
- Flue supports Cloudflare Workers AI model specifiers, which avoids requiring a third-party provider key. Its route middleware can authenticate a direct HTTP caller before durable admission, but QuizPilot instead dispatches host-authorized signals from its Hono API and does not expose the agent's HTTP router.
- A native, application-owned Durable Object is the appropriate authority for a live quiz room. Cloudflare recommends its hibernating WebSocket API; the object must rebuild connection identity from serialized socket attachments after eviction and retain authoritative game state in Durable Object storage.
- D1 is suitable for durable host/source/quiz/result records, but not a write for every live answer under load because it serializes database queries. The room Durable Object will score and persist a completed question/room summary in batches.
- A public-repository README Deploy to Cloudflare URL can provision Workers, D1, R2, Durable Objects, and Workers AI from `wrangler.jsonc`. It cannot provide secrets; QuizPilot will use Workers AI rather than an external model key.
- Browser uploads will use a Worker-mediated R2 `put()` request rather than R2 presigned URLs: source documents are intentionally small, this avoids R2 API credentials/CORS configuration, and it keeps upload authorization in the application.

- Reuse the `orders-demo` conventions for Hono middleware/error handling, additive D1 migrations, and real local-Worker integration tests. Do not copy its TypeScript setup, vanilla frontend, order/session domain, or its `run_worker_first: true` asset strategy; QuizPilot is JavaScript, Astro/shadcn, and needs new Durable Object, WebSocket, Workers AI, R2, Browser Run, and frontend infrastructure.
- Its narrow integration pattern is a `node:test` suite started by `scripts/integration.mjs`: create a temporary persistence directory, apply local D1 migrations, start local Wrangler, poll the health endpoint, then execute the suite. QuizPilot will retain this real-runtime verification pattern.

- Flue is suitable for the persistent host conversation and structured quiz-draft generation, but not for the game transport. Its documented transport is durable HTTP admission and replayable history/SSE; an application-owned Room Durable Object will own WebSocket admission, answer scoring, game state, and fan-out.
- Use exactly one Flue agent export, `QuizDrafter`, addressed only through trusted server-side `dispatch()` calls with the quiz ID as its durable conversation ID. Configure Vite with `flue({providers:['cloudflare']})` before `cloudflare({config:flueWorkerConfig()})`, use `useModel('cloudflare/@cf/moonshotai/kimi-k2.6')`, and append the generated `FlueQuizDrafterAgent` as a SQLite Durable Object migration. Do not install the optional `agents`, `@flue/sdk`, or `@cloudflare/sandbox` packages; the application never exposes a direct agent route, browser client SDK, or sandbox.

- The requested browser is Cloudflare Kitesurf, not Kite ML: Kite ML's documented CLI/MCP covers robotics datasets and simulation, while Kitesurf is Cloudflare's agent-oriented browser. Kitesurf runs through the Worker `BROWSER` binding, can extract rendered Markdown with `quickAction('markdown', {url, browser:'kitesurf'})`, and needs no API token from a Worker.
- Browser Run Quick Actions require Worker compatibility date `2026-03-24` or newer and remote mode during development. Kitesurf cannot reliably complete bot challenges or long-running authenticated sessions; QuizPilot will accept public, unauthenticated HTTPS webpages only and show source retrieval failure rather than silently falling back.
- Astro supports shadcn/ui through its React integration and Tailwind. shadcn's CLI supports JavaScript components through `components.json` with `tsx: false`; generated interactive components are `.jsx` islands while pages/layouts remain `.astro`.
- Flue custom tools treat model arguments as untrusted. Kitesurf retrieval will therefore be authorized by the Hono source route for the host-selected URL, stored as an immutable source snapshot, and passed to the agent as a trusted signal; the model will not receive a browser tool that can visit arbitrary URLs.

## Approach

### 1. Create the independently deployable Worker application

Create sibling repository `quizpilot` as an Astro static-site project with React islands, all authored in JavaScript: `.astro` pages/layouts, `.jsx` interactive islands and shadcn components, and `.js` Worker/agent/test code. Add `jsconfig.json`, Astro, `@astrojs/react`, React, Tailwind, shadcn/ui, Hono, `@flue/runtime`, Valibot, and Wrangler. Set `components.json` to `{ "style": "new-york", "rsc": false, "tsx": false, "tailwind": { "cssVariables": true }, "iconLibrary": "lucide" }`; do not introduce TypeScript or TSX.

Use two explicit builds: `astro.config.mjs` prerenders the UI to `dist/client`; `vite.worker.config.js` applies `flue({providers:['cloudflare']})` before `cloudflare({config:flueWorkerConfig()})` and emits the Worker to `dist/worker`. Define `dev:ui` for Astro, `dev:worker` for the Worker, `build:ui`, `build:worker`, `build`, `test`, `test:integration`, `package`, and `check`; `check` runs build, the two test commands, and `wrangler deploy --dry-run`. The Astro development server proxies `/api` and `/ws` to `dev:worker`; integration tests serve the built `dist/client` from the Worker so they exercise the deployed topology.

Author `wrangler.jsonc` with `nodejs_compat`, compatibility date `2026-10-23`, enabled observability, `assets.directory` `./dist/client`, D1 binding `DB`, R2 binding `SOURCES`, Workers AI binding `AI`, Browser Run binding `BROWSER` (with `remote: true` for local Quick Actions), application Room Durable Object binding `QUIZ_ROOM`, the Flue-generated agent migration `flue-quiz-drafter-v1`, and application room migration `quiz-room-v1`. Route `/api/*` and `/ws/*` through the Worker before SPA static-asset handling; all other client routes use SPA fallback. Declare resource names suitable for the Cloudflare Deploy Button and never commit account IDs, API keys, or generated resource IDs.

Add `README.md` with the exact public-repository Deploy Button form `https://deploy.workers.cloudflare.com/?url=https://github.com/<OWNER>/quizpilot`; replace `<OWNER>` only when the repository is published. State that the button provisions resources into the deployer's authenticated Cloudflare account, requires Cloudflare authorization, and has no local setup or external model secret. Include `.dev.vars.example` with no required model secret and never create a real local secret file.

### 2. Establish durable ownership, source ingestion, and publishable quiz drafts

Implement `src/worker/domain.js` as the single validation/normalization boundary. Export literal string arrays for `SOURCE_KINDS = ['paste', 'url', 'text_upload', 'generate']`, `QUIZ_STATUSES = ['draft', 'published', 'archived']`, and `GAME_STATUSES = ['lobby', 'question_open', 'question_closed', 'finished']`, plus parsers for host briefs, source payloads, quiz proposals, host controls, aliases, room codes, and answer messages. Enforce a draft of 2–20 questions, each with 2–4 non-empty options, exactly one valid `correctIndex`, a 5–120-second timer, rationale, and either one-or-more source citations or the explicit `AI-generated` provenance. Reject invalid JSON with `INVALID_JSON`, invalid input with a field-specific `INVALID_INPUT`, and payloads above the endpoint limit with `BODY_TOO_LARGE`.


Create `migrations/0001_initial.sql` using SQLite `STRICT` tables: `host_sessions`, `quizzes`, `sources`, `questions`, `games`, `players`, and `answers`. Store only SHA-256 hashes of opaque host and player tokens; index every owner lookup (`host_session_id, updated_at`) and room lookup (`join_code`). Store source metadata and R2 object keys in D1; write pasted text, Kitesurf-extracted Markdown, and uploaded document bytes to `SOURCES` under `sources/<quizId>/<sourceId>`. Store question options/citations as JSON text, and answer/result records separately from current live state. The `answers` row contains `received_at_ms`, `elapsed_ms`, selected option, correctness, and awarded score; a unique constraint on `(game_id, player_id, question_position)` prevents a second persisted answer.

In `src/worker/app.js`, create a Hono app that applies security headers, `Cache-Control: no-store` to all `/api/*` responses, a JSON body limit, and same-origin enforcement for unsafe browser requests. `GET /api/health` probes D1 and returns `{ok:true, application:'quizpilot'}`. `POST /api/v1/host-session` creates a seven-day HttpOnly, Secure, SameSite=Strict `qp_host` cookie. All draft, source, chat, question, and game-control routes require that host session and scope every D1 query by its session ID; return `401 SESSION_REQUIRED` before any object existence detail leaks.
Implement these host endpoints exactly:


- `POST /api/v1/quizzes` creates one `draft` quiz from `{title, audience, learningGoal}`.
- `GET /api/v1/quizzes` returns only the caller's draft/published quizzes; `GET /api/v1/quizzes/:quizId` returns its editable source, questions, and publication state.
- `PUT /api/v1/quizzes/:quizId/source/url` accepts one public, unauthenticated `https:` URL without credentials, localhost, or a literal loopback/private/link-local/reserved IP address. Call `env.BROWSER.quickAction('markdown', {url, browser:'kitesurf', gotoOptions:{waitUntil:'networkidle0'}})`, require a successful non-empty result, normalize/truncate it to 60,000 characters, write the Markdown to `SOURCES`, and persist the original URL plus captured-at timestamp. On browser action error, bot challenge, unsupported rendering, or empty result return `SOURCE_UNREADABLE` and retain the prior source; never fall back to unrendered `fetch()` or `HTMLRewriter`.
- `PUT /api/v1/quizzes/:quizId/source/paste` accepts bounded UTF-8 text and writes it to `SOURCES`; `PUT /api/v1/quizzes/:quizId/source/upload` accepts only `text/plain` or `text/markdown` under 512 KiB and writes it to `SOURCES`; `PUT /api/v1/quizzes/:quizId/source/generate` stores the host brief without an external source. All source object keys use `sources/<quizId>/<sourceId>`. The interface labels the upload option “text document”; PDF/Office parsing is intentionally not represented as supported input.
- `PUT /api/v1/quizzes/:quizId/questions` validates and atomically replaces the entire draft question set. It accepts only host-owned draft quizzes; published quizzes are immutable and return `409 QUIZ_NOT_EDITABLE`.
- `POST /api/v1/quizzes/:quizId/publish` revalidates source provenance and question constraints, changes `draft` to `published`, and returns a permanent host-visible quiz URL. `POST /api/v1/quizzes/:quizId/games` creates a new `lobby` game with a collision-checked six-character uppercase join code; only a published quiz can create a game.

Use bound D1 parameters and batched writes. Never use D1 as the active per-answer scoreboard; it is only the durable application record.

### 3. Add the Flue quiz-design conversation with host review as the commit boundary

Create `src/worker/agents/quiz-drafter.js` as the sole `'use agent'` module, export `QuizDrafter`, and assign the stable literal `QuizDrafter.agentName = 'quiz-drafter'`. Add `src/worker/skills/quiz-authoring/SKILL.md`, import it with `useSkill`, and make it the agent's quality contract: create assessable questions at the host's requested difficulty, cite exact captured evidence, reject unsupported claims, avoid ambiguous distractors, and state when the selected source cannot answer the brief. `QuizDrafter` uses `useModel('cloudflare/@cf/moonshotai/kimi-k2.6')` and returns JSON-only `QuizDraftProposal` output with `{label, excerpt}` citations or explicit `AI-generated` provenance. It has no write tools, network tools, filesystem, sandbox, or subagents.

Add `POST /api/v1/quizzes/:quizId/draft-runs`. After host/draft ownership validation, it reads the immutable selected source snapshot from R2 (or the stored generation brief), limits it to 60,000 characters, and calls `dispatch(QuizDrafter, {id: quizId, message:{kind:'signal', type:'quiz.draft.requested', body:JSON.stringify({instruction:<validated host chat text>, source:{id:sourceId, kind:sourceKind, label:sourceLabel, content:<source snapshot>}}), attributes:{quizId, sourceId, sourceKind, sourceLabel}}})`. Return the `DispatchReceipt.submissionId` with `202`; never accept a source URL, source ID, or quiz ID from the model. Add `GET /api/v1/quizzes/:quizId/draft-runs/:submissionId` as host-scoped Server-Sent Events: use `init(QuizDrafter,{id:quizId}).read(receipt,{onEvent})` to stream durable Flue events and the final proposal, returning `AGENT_RUN_FAILED` when the submission fails or aborts.

The Astro host island submits chat through that API, consumes the SSE stream, parses only a domain-valid `QuizDraftProposal`, and sends it to `PUT /api/v1/quizzes/:quizId/questions`. That endpoint remains the sole draft mutation boundary, so a model response cannot modify any quiz by selecting an ID. Render generated questions as uncommitted editable cards; the host can change text/options/correct answer/timer, delete, reorder, and regenerate before clicking Publish. Do not add an auto-publish path or an AI-based answer scoring path.


### 4. Implement a single authoritative live-game room

Create `src/worker/cloudflare.js` exporting `QuizRoom` as the application-owned Durable Object and declare only its `QUIZ_ROOM` binding manually. `POST /api/v1/games/:joinCode/join` validates a 1–30-character alias, creates a player token scoped to that game, stores its hash in D1, and sets the short-lived HttpOnly `qp_player` cookie. `GET /ws/games/:joinCode` and `GET /ws/games/:joinCode/host` validate the corresponding player/host cookie in Hono, then proxy the upgrade to the deterministic `QUIZ_ROOM` ID for that game with the verified role and identity in the request to the Durable Object.
`QuizRoom` is initialized by the successful game-creation route through an internal request carrying the immutable published question set; it writes that snapshot and initial lobby state to Durable Object SQLite before the API returns a join code. Its persisted state contains `{status, questionPosition, openedAtMs, deadlineMs, answersByPlayer, scoreboard}`. When `open_question` arrives, record `openedAtMs = Date.now()` and `deadlineMs = openedAtMs + timerSeconds * 1000` before broadcasting. On `answer`, capture `receivedAtMs = Date.now()` at admission, calculate `elapsedMs = receivedAtMs - openedAtMs`, accept only the first valid answer strictly before `deadlineMs`, and persist the answer record to Durable Object storage before its accepted event. Never accept a client clock, client elapsed time, or client score.

Use `ctx.acceptWebSocket`, attach `{role, playerId}` to every accepted socket with `serializeAttachment`, reconstruct socket membership from `ctx.getWebSockets()` in the constructor, and implement `webSocketMessage`/`webSocketClose` so hibernation loses no role or score state. Accept exactly these JSON client message types: host `start`, `open_question`, `close_question`, `next_question`, `finish`; player `answer` with one option index. Reject wrong-role, wrong-state, late, malformed, duplicate, or out-of-range messages with an error event and no state mutation.

On `close_question`, calculate score from persisted server `elapsedMs`, broadcast correctness and the ordered leaderboard, then batch-write answer timestamps, scores, and player totals to D1. On `finish`, persist terminal game/result records and broadcast `game_finished`. The host may not alter correct answers once a game is created; a new game is required after a quiz edit.

### 5. Deliver the host and player interface

Build one static Astro shell at `src/pages/index.astro` and hydrate `src/components/app-shell.jsx` with `client:load`. `app-shell.jsx` derives the current view from `window.location.pathname` and handles History API navigation for `/`, `/host/quiz/:quizId`, `/play/:joinCode`, and `/game/:joinCode`; this preserves shareable URLs while the Worker SPA fallback serves the static shell. Define API request/response and WebSocket event names once in JSDoc-documented `src/shared/protocol.js`, then import them into the Worker and React islands; do not duplicate payload literals across handlers.

Generate shadcn JavaScript primitives through its CLI into `src/components/ui/`: `Button`, `Card`, `Dialog`, `Drawer`, `Input`, `Label`, `Select`, `Textarea`, `Tabs`, `Progress`, `Skeleton`, `Toast`, and `Tooltip`; add its AI `Chat`, `Prompt Input`, `Sources`, and inline citation primitives for the drafting view. Build a calm, content-first workflow rather than a marketing landing page: the host dashboard starts with one “Create quiz” action, the quiz workspace shows Source → AI draft → Review → Publish as progressive stages, and the live projector prioritizes readable join code, countdown, question, and leaderboard. Use the shadcn New York neutral tokens, one high-contrast action color, 44px minimum touch targets, visible focus, color-independent correctness states, and no decorative gradients or custom component library.

The source stage presents Paste text, Website URL, Text document, and Create from brief as mutually exclusive cards. URL submission remains pending while Kitesurf extracts Markdown, then shows URL, captured-at time, excerpt, and a retrieval failure with retry; it cannot proceed on an empty capture. The chat stage streams the server-sent Flue events into the AI chat component and shows citations as expandable source cards. The review stage renders editable proposal cards with provenance badges and keeps Publish disabled until server validation succeeds. The projector shows lobby join code, QR target `/play/<joinCode>`, countdown, question/options, post-question correctness, and leaderboard. The player view sends one answer, locks locally after the event is accepted, and reconciles to the authoritative room snapshot after reconnect; it never displays client-derived time or score.

### 6. Verify the actual contracts and deployment package

Add `node:test` JavaScript unit tests for malformed proposals, citation/AI provenance, question/timer bounds, Kitesurf result normalization, and invalid room role/state transitions. Add a real Worker integration harness modeled on `orders-demo/scripts/integration.mjs`: run `npm run build`, apply the D1 migration to temporary persistence, start the built Worker with Wrangler, poll `GET /api/health`, then execute HTTP/WebSocket tests against it. Browser Run Quick Actions are account-remote only, so this local harness uses pasted text and never fakes a successful Kitesurf extraction.

The integration scenario must create a host session; create a pasted-text quiz; submit an invalid proposal and receive `400 INVALID_INPUT`; submit a valid sourced two-question proposal; publish it; create a game; join two aliases; prove a non-host cannot start the game; connect host and players over WebSocket; prove server receipt time is recorded for the first valid answer, a duplicate and a post-deadline answer are rejected, the ordered leaderboard is broadcast, and the finished game persists exactly one timestamped answer per player/question. Add a second scenario where a `generate` source proposal is accepted only with `AI-generated` provenance and a source-based proposal without citations is rejected.

Run from `quizpilot`: `npm run build`, `npm test`, `npm run test:integration`, and `npm run package`. With Cloudflare credentials, start the Worker in remote mode and submit `https://example.com` through the Website URL flow; observe Kitesurf Markdown, source capture time, citation-bearing AI proposal, and failure display for a deliberately unsupported/bot-protected URL. Manually open the built app once as host and two browser contexts as players to verify source selection, streamed Flue review, publish gating, room join, an open/answer/close cycle, reconnect snapshot, recorded timing, and mobile player layout. For the Deploy Button, publish the repository, open its generated button URL while authenticated to a disposable Cloudflare account, confirm all declared resources are provisioned, and verify the deployed health endpoint and static host page; do not claim anonymous deployment.

## Critical files & anchors

- `quizpilot/wrangler.jsonc` — Astro static asset binding, Browser Run/AI/D1/R2/Room bindings, and ordered Durable Object migrations; Flue-generated bindings stay out of this file.
- `quizpilot/src/worker/app.js` — Hono security/session/source/Kitesurf/drafting routes and WebSocket proxy boundary.
- `quizpilot/src/worker/agents/quiz-drafter.js` — Flue identity, Workers AI model, and `quiz-authoring` skill composition; it intentionally has no mutation or browser tools.
- `quizpilot/src/worker/cloudflare.js` — `QuizRoom` hibernating WebSocket lifecycle, receipt timestamp authority, game transitions, and D1 persistence boundary.
- `quizpilot/src/pages/index.astro` and `quizpilot/src/components/app-shell.jsx` — static Astro entry and shadcn JavaScript island/router for all host, player, and projector views.

## Assumptions & contingencies

- The public repository will be `github.com/<OWNER>/quizpilot`; retain the literal owner placeholder in the README until the repository exists, then replace it before testing the Deploy Button.
- Workers AI model availability can vary by account. If `cloudflare/@cf/moonshotai/kimi-k2.6` is unavailable at deployment, retain the same Flue `QuizDrafter` contract and replace only the model specifier with an account-available Workers AI chat model; do not introduce a third-party model key.
- A host's ownership is intentionally an opaque browser cookie for this public portfolio demo. If that cookie is cleared, the existing host dashboard is inaccessible; do not add account recovery or a login system.
- Text documents are deliberately limited to UTF-8 plain text/Markdown. If a future requirement needs PDF/Office documents, add a separate extraction pipeline and source-type contract rather than treating binary content as text.
